# French Learning Constitution

Приложение для систематизации материалов уроков французского языка: база знаний,
интерактивный сборник упражнений и словарь с интервальным повторением. Контент наполняется
агентом Claude Code из материалов уроков (фото, PDF, документы, ссылки) и вручную.

Ключевые слова: **ДОЛЖЕН / НЕ ДОЛЖЕН** — обязательное правило; **СЛЕДУЕТ** — рекомендация,
отступление от которой требует обоснования.

## Core Principles

### I. Достоверность и прослеживаемость знаний (НЕПРЕЛОЖНЫЙ)

- Каждый элемент знаний (слово, правило, текст, упражнение, ответ, перевод, заметка) ДОЛЖЕН
  хранить своё происхождение: материал урока (с указанием исходного файла), внешний ресурс
  (со ссылкой), добавлено пользователем, создано ИИ, получено от внешнего сервиса.
- Всё, что создано ИИ или внешним сервисом (ответы к упражнениям, переводы, примеры,
  объяснения, переведённые формулировки заданий), ДОЛЖНО быть помечено как таковое.
- ИИ НЕ ДОЛЖЕН выдавать сгенерированный контент за материал преподавателя.
- Происхождение ДОЛЖНО быть доступно в интерфейсе, но его отображение НЕ ДОЛЖНО мешать чтению
  материала (например, включается переключателем).

**Обоснование**: пользователь учится по этой базе и должен всегда знать, чему можно доверять
полностью, а что стоит перепроверить. Это же основа для будущего ИИ-репетитора, который обязан
различать ответы «по материалам» и «от себя».

### II. Пользователь определяет состав контента

- Пользователь решает, какие материалы и задания попадают в приложение и с каким статусом
  (основное, необязательное, резерв). Статус ДОЛЖЕН быть изменяемым позже.
- Контент появляется четырьмя путями: обработка материалов урока агентом, добавление агентом
  по ссылке, ручное добавление пользователем в приложении, генерация ИИ по явному запросу.
  Все пути ДОЛЖНЫ соблюдать единый формат (принцип V) и указывать происхождение (принцип I).
- Агент НЕ ДОЛЖЕН отбрасывать материал молча: всё пропущенное, нераспознанное или отложенное
  ДОЛЖНО быть явно указано в отчёте.

**Обоснование**: не всё из материалов урока нужно учить; решение принадлежит пользователю,
а не агенту.

### III. Проверка по исключению

- Агент ДОЛЖЕН самостоятельно проверять результат обработки (распознанный текст, решённые
  ответы).
- Места, в которых агент не уверен, ДОЛЖНЫ быть явно помечены и вынесены пользователю
  на проверку. Остальной контент доступен сразу, без ручного одобрения.
- После каждой обработки агент ДОЛЖЕН выдавать отчёт: что добавлено, что пропущено, что
  требует проверки.
- В приложении ДОЛЖНА быть возможность сообщить об ошибке в контенте или правильном ответе.

**Обоснование**: баланс между качеством контента и временем пользователя — проверяется только
сомнительное, а ошибки, найденные позже, исправляются через обратную связь.

### IV. Интерактивный интерфейс вместо картинок (НЕПРЕЛОЖНЫЙ)

- Материалы ДОЛЖНЫ превращаться в структурированные данные и отображаться как интерфейс:
  форматированный текст, таблицы, интерактивные упражнения с автоматической проверкой.
- Исходные файлы служат только источником для сверки, а не основным видом контента. Они
  хранятся в сжатом виде, достаточном для сверки.
- Каждое упражнение ДОЛЖНО относиться к одному из поддерживаемых типов. Для упражнений, не
  подходящих ни под один тип, используется запасной тип «открытый ответ», и агент ДОЛЖЕН
  сообщить о новом типе.

**Обоснование**: скриншоты нельзя выполнять, проверять, искать и связывать между собой;
структурированные данные — можно.

### V. Единый формат и многомерная структура контента

- Формат хранения контента ДОЛЖЕН быть строго описан; он является договором между агентом
  и приложением.
- Приложение ДОЛЖНО проверять контент при загрузке; ошибочный элемент показывается как ошибка
  и НЕ ДОЛЖЕН ломать остальное приложение.
- Формат меняется только через спецификацию, с переводом существующего контента на новую
  версию формата.
- Знания хранятся мелкими самостоятельными элементами (отдельное правило, слово, упражнение,
  заметка) с постоянными идентификаторами.
- Каждый элемент ДОЛЖЕН быть описан признаками: урок (необязательно — у материалов из
  интернета и собственных добавлений урока может не быть), часть урока (классная / домашняя
  работа), вид (теория, лексика, текст, упражнение, заметка), тема. Это позволяет показывать
  контент разными группировками без изменения данных.

**Обоснование**: агент пишет, приложение читает — «поплывший» формат тихо ломает всё.
Мелкие связанные элементы нужны для разных способов просмотра и для будущего ИИ-репетитора.

### VI. Разделение кода, контента и личных данных (НЕПРЕЛОЖНЫЙ)

- Код приложения хранится в публичном репозитории.
- Учебные материалы, созданный из них контент, заметки и личные данные (ответы, прогресс)
  ДОЛЖНЫ храниться в отдельном приватном хранилище и НЕ ДОЛЖНЫ попадать в публичный
  репозиторий.
- Для приватных данных ДОЛЖНА существовать резервная копия; изменения контента ДОЛЖНО быть
  возможно откатить.
- Пути к хранилищам ДОЛЖНЫ задаваться настройкой, а не быть зашиты в код.

**Обоснование**: материалы принадлежат преподавателю, а история обучения — личные данные.
Настраиваемые пути позволяют позже перенести приложение на сервер или в контейнер.

### VII. Сохранность истории обучения

- Каждая попытка выполнения упражнения и каждое повторение карточки ДОЛЖНЫ сохраняться с датой
  и результатом и НЕ ДОЛЖНЫ удаляться или перезаписываться.
- Изменение контента (исправление ответа, смена статуса упражнения) НЕ ДОЛЖНО уничтожать
  связанную историю.

**Обоснование**: история нужна для отслеживания прогресса, работы над ошибками и будущего
ИИ-репетитора. По объёму она пренебрежимо мала.

### VIII. Корректность французского языка

- Языковые особенности — обязательная часть данных: диакритические знаки, род и артикль
  существительных, словарная форма слова, спряжение.
- Проверка ответов ДОЛЖНА быть строгой ко всему языковому: буквы, диакритика (é, è, ê, à, ç,
  œ и др.), дефисы в словах ДОЛЖНЫ совпадать с правильным ответом. Ошибка только в диакритике
  засчитывается как ошибка (подсказка о характере ошибки допустима).
- Различия, связанные только с набором на клавиатуре (вид апострофа ' и ’, регистр, лишние
  пробелы), НЕ ДОЛЖНЫ считаться ошибкой.
- Проверка ДОЛЖНА поддерживать несколько правильных вариантов ответа.

**Обоснование**: ошибка в данных или слишком мягкая проверка закрепляют неправильное
написание; слишком жёсткая проверка на клавиатурные мелочи мешает заниматься.

### IX. Ядро работает без внешних сервисов

- Основные функции (уроки, упражнения, словарь, карточки, заметки, прогресс) ДОЛЖНЫ работать
  без интернета, внешних сервисов и LLM.
- Внешние сервисы допустимы только для дополнительных функций (перевод, озвучка, будущий
  ИИ-репетитор). При их недоступности приложение ДОЛЖНО продолжать работать, а функция —
  сообщать о временной недоступности.
- Во внешние сервисы ДОЛЖЕН передаваться только необходимый минимум (например, выделенное
  слово или фраза), но не материалы урока целиком.

**Обоснование**: учиться должно быть можно всегда; приватность материалов сохраняется.

### X. Экономия ресурсов ИИ

- Агент ДОЛЖЕН обрабатывать только то, что пользователь явно попросил.
- Дорогие операции (массовая генерация переводов, примеров, упражнений, объяснений) ДОЛЖНЫ
  выполняться только по отдельному запросу пользователя.

**Обоснование**: токены стоят денег. Принцип может быть смягчён поправкой, если качество
обработки материалов окажется недостаточным.

### XI. Простота и поэтапность

- Приложение рассчитано на одного пользователя и запускается на его компьютере.
- НЕ СЛЕДУЕТ заранее строить то, что не нужно текущей функции (контейнеризация, развёртывание
  на сервере, интеграция LLM по API), но архитектурные решения НЕ ДОЛЖНЫ закрывать к этому
  дорогу.
- Каждая функция ДОЛЖНА приносить пользу сама по себе и быть пригодной к использованию до
  реализации следующих.
- Интерфейс ДОЛЖЕН с первого дня быть удобным на узком экране телефона.

**Обоснование**: защита от переусложнения; адаптивная вёрстка сразу почти бесплатна, а
переделка потом дорога — доступ с телефона запланирован.

### XII. Защита доступа

- По умолчанию приложение ДОЛЖНО быть доступно только с компьютера, на котором запущено.
- Доступ с других устройств допустим только через защищённый канал (приватная сеть или вход
  с паролем).

**Обоснование**: в приложении личные данные и чужие учебные материалы.

### XIII. Тесты пишутся до кода (НЕПРЕЛОЖНЫЙ)

- Для критичной логики ДОЛЖЕН применяться цикл TDD: сначала тест, который не проходит, затем
  код, после которого тест проходит, затем рефакторинг.
- Критичная логика: проверка ответов, алгоритм интервальных повторений, проверка формата
  контента при загрузке, подсчёт прогресса.
- Интерфейс проверяется вручную по сценарию quickstart функции.

**Обоснование**: ошибки в этой логике незаметны глазом, но напрямую портят обучение.

## Constraints (Ограничения и условия)

- **Пользователь**: один, без регистрации.
- **Платформа**: веб-приложение в браузере на компьютере; доступ с телефона — позже.
- **Языки**:
  - интерфейс, документация проекта (спецификации, планы, задачи) и заметки — на русском;
  - учебный контент — на французском с переводом на русский;
  - формулировки заданий в упражнениях (на английском или французском) переводятся на
    русский, оригинал сохраняется; содержание упражнений (предложения, тексты, варианты)
    остаётся на французском, если задание не требует иного;
  - код, имена файлов и идентификаторы — на английском.
- **Наполнение**: агентом Claude Code по инструкции (навыку) и вручную в приложении;
  LLM внутри приложения на текущем этапе нет.
- **Внешние сервисы на текущем этапе**: сервис перевода. Озвучка французского — локальная
  нейросеть (Piper) на компьютере пользователя, без обращения к внешним сервисам.
- **Технологический стек**:
  - язык — Python 3.12; зависимости и запуск — через `uv`;
  - веб-сервер — FastAPI; страницы собираются на сервере (шаблоны), интерактивность —
    HTMX и Alpine.js без отдельной сборки фронтенда; библиотеки JavaScript хранятся в проекте
    локально (приложение работает без интернета, принцип IX);
  - прогресс и настройки — SQLite (один файл в приватном хранилище);
  - контент — читаемые файлы в приватном git-репозитории; схема формата описана в коде
    один раз и используется и приложением, и проверкой контента агентом (принцип V);
  - тесты — pytest; линтер и форматтер — ruff;
  - вспомогательные скрипты агента (проверка формата, сжатие изображений) — на Python
    в этом же репозитории.
  Отступление от стека допускается только с обоснованием в плане функции (Complexity
  Tracking).
- **Хранилища**: код — публичный репозиторий `Katalien/french_learning`; контент и данные
  прогресса — приватный репозиторий `Katalien/french_learning_materials` (локально —
  соседняя папка, путь задаётся настройкой); исходные материалы преподавателя — папка
  пользователя вне обоих репозиториев.

## Development Workflow (Процесс разработки)

### Цикл разработки

- Каждая функция проходит цикл Spec Kit: `/speckit-specify` → `/speckit-clarify`
  (обязательно) → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` (рекомендуется) →
  `/speckit-implement`.
- Спецификации (`specify` + `clarify`) МОГУТ готовиться заранее и коммититься в `main`,
  так как это документы, а не код. Реализация каждой функции (`plan` и далее) ведётся
  в отдельной ветке `NNN-название`, которая вливается в `main`, когда функция готова.
- Документы ДОЛЖНЫ соответствовать коду: при изменении поведения сначала обновляется
  спецификация (или выполняется `/speckit-converge`).
- Функция считается готовой, когда выполнены критерии успеха из её спецификации, все тесты
  проходят и сценарий quickstart проверен вручную.

### Контроль качества

- Перед каждым коммитом все тесты ДОЛЖНЫ проходить; коммит с падающими тестами запрещён.
- Push в `main` — только при проходящих тестах. Слияние ветки функции в `main` — только после
  приёмки пользователем.
- Обходить проверки ЗАПРЕЩЕНО (например, `git commit --no-verify`, отключение или ослабление
  теста ради прохождения). Если тест мешает, сначала выясняется причина.
- Код ДОЛЖЕН проходить линтер и форматтер без ошибок (инструменты определяются стеком).
- Техническая защита (git-хуки и CI, запускающие тесты и линтер) ДОЛЖНА быть настроена
  в первой функции с кодом и в дальнейшем НЕ ДОЛЖНА отключаться.

### Документация

- `README.md` ДОЛЖЕН описывать проект, установку и запуск; обновляется при изменении способа
  запуска.
- `CLAUDE.md`: раздел «Команды» (запуск приложения, тестов, линтера) ДОЛЖЕН быть актуальным.
- `docs/roadmap.md`: статус функции ДОЛЖЕН обновляться при переходе между этапами.
- `CHANGELOG.md` ДОЛЖЕН пополняться при завершении каждой функции: что появилось, что
  изменилось.
- Комментарии в коде СЛЕДУЕТ писать только там, где логика неочевидна.

### Коммиты и секреты

- Коммиты небольшие и осмысленные; сообщения в стиле `feat:` (новое), `fix:` (исправление),
  `docs:` (документация), `test:` (тесты), `refactor:` (переработка), `chore:` (служебное).
- Материалы уроков и личные данные НИКОГДА не коммитятся в публичный репозиторий.
- Секреты (ключи API, пароли, токены) НИКОГДА не коммитятся. Они хранятся в локальном файле
  настроек, исключённом из git; в репозитории — только пример файла без значений.

## Governance

- Конституция имеет приоритет над остальными документами проекта. Каждый план ДОЛЖЕН проходить
  раздел «Constitution Check»; любое отступление ДОЛЖНО быть обосновано в разделе
  «Complexity Tracking» плана.
- Конституция изменяется командой `/speckit-constitution` с повышением версии по правилам
  семантического версионирования:
  - MAJOR — принцип удалён или изменён по смыслу;
  - MINOR — добавлен принцип или раздел, существенно расширены правила;
  - PATCH — уточнение формулировок без изменения смысла.
- При изменении конституции СЛЕДУЕТ проверить, не противоречат ли ей существующие
  спецификации и планы.
